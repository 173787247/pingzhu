- 加成有不会衰减到零的地板（1.5 以上），并在 `firstSeen` 视窗内保留最高级

- 候选视窗：一页十个（`1234567890`），空白键翻页，`←→` 移动游标

**实测**（`node engine/bench-learn.mjs 5000`，模拟使用者只更正一次）：

| 指标 | 学习前 | 学习后 |
|---|---|---|
| top-1 准确率 | 90.38% | **99.54%** |
| 同音词平手 | 480 | 21 |

教 492 个词、修好 464 例；回退 6 例（5 例是测试集本身的必然碰撞，1 例是已知的
「学习全域影响路径」副作用，机率 0.02%，已记录于 [06](06-engine-design.md)）。

**这一项证明了 M2 的核心命题**：同音词不需要靠模型猜对，靠「教一次就记住」更快。

### M3 · Rust 核心 ＋ C ABI ✅

- `core-rs/`：音节模型、键盘、词库、读字格、使用者词库、输入引擎、C ABI
- `include/pingzhu.h`：外壳唯一需要看的介面
- **验证方式是这一段的重点**：TypeScript 版是规格书，
  `tests/differential.rs` 重播 1,529 个从参考实作汇出的真实按键字串，
  逐项比对 composing／sentence／score／usedFallback／断词／候选第一页
- 突变测试确认这个绿色是有意义的（关闭 promotion → 20+ 处不一致）
- 纯 C 烟雾测试：一个 C 程式用 C ABI 驱动引擎，得出 你好／我爱你／万丹

**一个诚实的结果：移植并没有变快。** 16.5 µs vs 15.2 µs，同一个数量级。
Rust 的价值在于**能被嵌进别人的行程**（TSF 是 in-proc DLL、IMK 是 app bundle、
Android／鸿蒙需要 `.so`），不是速度。距离 10 ms 的体验门槛还有三个数量级，
所以刻意不做微观最佳化。

### M4a · Windows 可携版外壳 ✅

托盘常驻 + `WH_KEYBOARD_LL` 全域钩子 + 候选视窗 + `SendInput` 注入。

- 按键路由写成**不含 `<windows.h>` 的纯函式**，因此可以无头测试
- 引擎以 `LoadLibrary` 载入，ABI 版本不符时给出可读错误而不是崩溃
- 从 WSL 用 MSVC 交叉编译（`windows/build.sh`）

**验证**：Windows 原生 `pingzhu-router-test.exe`（按键路由）与
`pingzhu-engine-test.exe`（透过真实 DLL 驱动引擎：你好／我爱你／万丹／学习）。

**这个整合测试抓到一个真实缺陷**：`engine_create` 原本不附带使用者词库，
只有在词库档已存在时才装上——**全新安装的使用者永远学不了字**。已修。

**它做不到的**：不是 TSF，所以不进语言列，也无法对管理员权限的视窗输入（UIPI）。

### M4b · Windows TSF 外壳 ✅

实际做完的比原估的多，也比原估的久——但**风险估计是对的**（原本标「高」）。

| 项目 | 说明 | 状态 |
|---|---|---|
| 核心介面 | `ITfTextInputProcessorEx`、`ITfThreadMgrEventSink`、`ITfKeyEventSink`、`ITfCompositionSink` | ✅ |
| 组字 | `ITfContextComposition` 编辑会话，文字写进文件本身 | ✅ |
| 显示属性 | `ITfDisplayAttributeProvider`：组字中的注音加虚线底线 | ✅ |
| 候选视窗 | 自绘视窗（TSF 不提供候选 UI），用 `ITfContextView::GetTextExt` 定位到插入点 | ✅ |
| 安装程式 | COM 注册 + CTF 语言设定 + `InstallLayoutOrTip` + 反安装 | ✅ |
| 语言列按钮 | `ITfLangBarItemButton`：显示当前字形，左键切换、右键选单 | ⚠️ 见下 |
| 诊断 | `pingzhu-tsf.log`：主机行程名、引擎载入结果、按键是否抵达 | ✅ |
| 升级机制 | TSF DLL 档名带版本（Windows 锁住已载入的 DLL） | ✅ |

**这一段的实际代价，几乎全在「找不到原因」而不是「写不出来」。**

六次失败，每一次的症状都是「使用者说不能用」，而程式码看起来完全正确：

1. **资料目录差一层** —— 引擎要 `<dir>\bopomofo-lm.tsv`，服务传了 DLL 所在目录，
   而模型在 `<dir>\data\`。引擎载入失败 → 所有按键原样放行。**没有任何错误讯息。**
2. **日志永远是空的** —— `_wfopen(..., "ccs=UTF-8")` 开的是宽字元串流，用 `fprintf`
   写窄位元组会安静地什么都不写。**一个在最需要时刚好空白的日志，比没有日志更糟。**
3. **设定改了没反应** —— 读设定的程式码放在 `if (engineTried_) return;` 后面。
   引擎只需要载入一次，**设定不是**。
4. **数字键当成数字** —— 十个数字键都是注音键，而且好几个是声母。要求「已经在组字中」
   才让数字组字，等于让所有以 ㄅㄉㄓㄚㄞㄢ 开头的字都打不出来。
5. **语言列按钮加不上去** —— 少了 `GUID_TFCAT_TIPCAP_UIELEMENTENABLED` 类别注册。
   TSF 把「没说自己有 UI」的服务当成「没有 UI 可提供」，`AddItem` 回传 `E_FAIL`，
   **错误码不解释任何事**。
6. **测试通过但测到错的东西** —— 三次：日志印了一句永远成立的话；测试读了打包当下的
   旧执行档；测试走注册表所以测的是「已注册的 DLL」而不是命令列指定的那个。

**共同的形状**：失败是**安静的**。没有 crash、没有例外、没有错误讯息，
只有「使用者说没反应」和「程式码看起来对」。

**教训**：这段工作真正的产出不只是 TSF 外壳，还有 `pingzhu-tsf.log`
——**把安静的失败变成看得见的失败**。前四个问题都是靠它定位的。

**已知限制**：语言列按钮在部分环境被 `AddItem` 拒绝（`E_FAIL`）。已注册
`UIELEMENTENABLED` 类别后仍待实机确认。**不依赖语言列的 `Ctrl+Alt+S` 是可靠路径。**

### M7 · HarmonyOS NEXT 外壳 —— ✅ 真机验证完成

**2026-09-27 在 HUAWEI Mate XT（HarmonyOS 6.1，API 20）上：
`su3cl3` → 你好，字进了备忘录。**

完整路径：鸿蒙键盘 → ArkTS → NAPI → Rust 核心 → 解码 →
`InputClient.insertTextSync` → 备忘录。

**下面是动手之前的可行性调研，保留了。**

**已查证的结论**：框架**明文支持三方输入法**（官方文件写「面向…三方输入法应用」，
`hdc shell ime -e <bundle>` 明文支持启用三方输入法，并有官方范例 App **KikaInput**）。
**技术上可行。**

**真正的限制是治理，不是 API**：

| 限制 | 来源 | 对本专案的影响 |
|---|---|---|
| 基础访问模式**禁止网路互动** | 官方「约束与限制」原文 | 云端词库不可行——我们本来就不做，**无影响** |
| 未来将加严：独立沙箱、禁子进程、限 IPC | 同上 | 核心必须 **in-process**——我们的 C ABI 本来就是，**无影响** |
| 部分能力仅系统预设输入法可用（`12800010`） | API 文件 | 少数进阶功能拿不到，**可接受** |
| 签章／AGC／**侧载**／上架资质 | **【需查证】** | **这是真正的未知数** |

**验证计划（两周）**：

1. **先确认 AppGallery 上是否已有第三方中文输入法**（搜狗／百度／讯飞鸿蒙版）。
   这一题的答案决定一切：若已有且可设为预设 → 商业可行性立即确认；
   若确实没有 → 先行者机会。
2. 用 DevEco Studio 建最小 `InputMethodExtensionAbility`，实机上被列为可选输入法
3. ArkTS 写死小词表，打出「你好」
4. 确认 NAPI 能否载入自带的 C ABI 静态库

**成功** → M7 立项。**失败** → 改为「把引擎与词库开放给鸿蒙开发者」，不自建外壳。

**风险**：未知（但已从「未知的未知」降级为「已知的四个问题」）。因此**不先进排程**。

详见 [03-platform-matrix.md](03-platform-matrix.md)。

## 这个专案可能失败的方式

诚实列出，因为这比乐观的排程有用：

1. **Windows TSF 吃掉所有时间**（机率：中）。对策：先出可携版验证需求，TSF 后置。
2. **选字品质不如自然输入法，使用者试用后离开**（机率：中—高）。
   对策：M2 的学习能力与 bigram 模型是**必要**而非加分；并且要建立可量化的评测
   （首选正确率、KSPC），否则无法知道自己是进步还是退步。
3. **HarmonyOS 不允许第三方输入法**（机率：未知）。对策：见 M7 的退路。
4. **只有一个人做**（机率：高）。对策：里程碑切得够小，每个里程碑结束都有一个
   「可交付、可展示、可停止」的状态。M0 与 M1 已经符合这个标准。
