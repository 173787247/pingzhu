# 05 · 路線圖：從可運作的引擎到四平台產品

> 估時以「一位全職工程師、熟悉該平台」為基準。這是工程估算，不是承諾。

## 已完成

- 大千式、倚天式鍵盤表（權威來源轉錄並實測驗證）

## 待辦

### M2 · 個人化 ✅

- 使用者詞庫：以 **log10 加成**疊加在語言模型分數上，`final = lmScore + userBonus`
- 加成有不會衰減到零的地板（1.5 以上），並在 `firstSeen` 視窗內保留最高級
- **只有明確選擇才算學習**；`commit()` 預設不記錄（理由見 [06](06-engine-design.md)）
- 純文字持久化，可 grep、可手改、可 diff
- 候選視窗：一頁十個（`1234567890`），空白鍵翻頁，`←→` 移動游標

**實測**（`node engine/bench-learn.mjs 5000`，模擬使用者只更正一次）：

| 指標 | 學習前 | 學習後 |
|---|---|---|
| top-1 準確率 | 90.38% | **99.54%** |
| 同音詞平手 | 480 | 21 |

教 492 個詞、修好 464 例；回退 6 例（5 例是測試集本身的必然碰撞，1 例是已知的
「學習全域影響路徑」副作用，機率 0.02%，已記錄於 [06](06-engine-design.md)）。

**這一項證明了 M2 的核心命題**：同音詞不需要靠模型猜對，靠「教一次就記住」更快。

### M3 · Rust 核心 ＋ C ABI ✅

- `core-rs/`：音節模型、鍵盤、詞庫、讀字格、使用者詞庫、輸入引擎、C ABI
- `include/pingzhu.h`：外殼唯一需要看的介面
- **驗證方式是這一段的重點**：TypeScript 版是規格書，
  `tests/differential.rs` 重播 1,529 個從參考實作匯出的真實按鍵字串，
  逐項比對 composing／sentence／score／usedFallback／斷詞／候選第一頁
- 突變測試確認這個綠色是有意義的（關閉 promotion → 20+ 處不一致）
- 純 C 煙霧測試：一個 C 程式用 C ABI 驅動引擎，得出 你好／我愛你／萬丹

**一個誠實的結果：移植並沒有變快。** 16.5 µs vs 15.2 µs，同一個數量級。
Rust 的價值在於**能被嵌進別人的行程**（TSF 是 in-proc DLL、IMK 是 app bundle、
Android／鴻蒙需要 `.so`），不是速度。距離 10 ms 的體驗門檻還有三個數量級，
所以刻意不做微觀最佳化。

### M4a · Windows 可攜版外殼 ✅

托盤常駐 + `WH_KEYBOARD_LL` 全域鉤子 + 候選視窗 + `SendInput` 注入。

- 按鍵路由寫成**不含 `<windows.h>` 的純函式**，因此可以無頭測試
- 引擎以 `LoadLibrary` 載入，ABI 版本不符時給出可讀錯誤而不是崩潰
- 從 WSL 用 MSVC 交叉編譯（`windows/build.sh`）

**驗證**：Windows 原生 `pingzhu-router-test.exe`（按鍵路由）與
`pingzhu-engine-test.exe`（透過真實 DLL 驅動引擎：你好／我愛你／萬丹／學習）。

**這個整合測試抓到一個真實缺陷**：`engine_create` 原本不附帶使用者詞庫，
只有在詞庫檔已存在時才裝上——**全新安裝的使用者永遠學不了字**。已修。

**它做不到的**：不是 TSF，所以不進語言列，也無法對管理員權限的視窗輸入（UIPI）。

### M4b · Windows TSF 外殼（4–6 週）

| 項目 | 說明 |
|---|---|
| 核心介面 | `ITfTextInputProcessor`、`ITfThreadMgr`、`ITfKeyEventSink`、`ITfDisplayAttributeProvider` |
| 候選視窗 | 自繪視窗（TSF 不提供候選 UI） |
| 安裝程式 | COM 註冊 + 語言設定登錄 + 反安裝 |
| 參考來源 | Microsoft `Windows-classic-samples`（MIT）、PIME（授權待審） |

**風險**：**高**。TSF 是四個框架裡最複雜的，COM 註冊、執行緒 apartment、
與 Windows 內建注音的共存都是歷史坑。這是整個專案最可能超支的一段。
**退路**：先出「免安裝的可攜版」（提供一個獨立的輸入視窗＋剪貼簿注入），
驗證使用者需求後再投入 TSF。

### M5 · macOS IMK 外殼（3–4 週）

| 項目 | 說明 |
|---|---|
| 核心介面 | `IMKInputController`、`IMKServer`、`Info.plist` 的 `tsInputModeListKey` |
| 候選視窗 | 自繪 |
| 簽章 | Developer ID + notarization（輸入法無法沙箱化，需明確說明） |
| 參考來源 | McBopomofo（MIT） |

**風險**：中。IMK 相對穩定，且有一個 MIT 的完整同類產品可以對照。
**注意**：macOS 沙箱與輸入法的關係需在實作初期確認（Mac App Store 對輸入法的限制）。

### M6 · Android 外殼（3–4 週）

| 項目 | 說明 |
|---|---|
| 核心介面 | `InputMethodService` + 自訂鍵盤 View（`CandidatesView` 已 deprecated，需自繪候選列） |
| 鍵盤佈局 | 注音 37 鍵 + 聲調鍵，手機直向需縮排設計（這是**設計**工作，不是工程工作） |
| JNI | Rust 核心透過 JNI |
| 發佈 | Google Play（輸入法類別需填寫資料安全表單） |

**為何值得優先**：商業競品在 Android **完全缺席**（見 [01](01-competitive-analysis.md)），
而 `InputMethodService` 是四個框架裡最單純的。**這是投報率最高的一段。**
**風險**：低—中。主要風險在輸入法 UI 的易用性，而非技術。

### M7 · HarmonyOS NEXT 外殼（未知，需先做可行性驗證）

**已查證的結論**：框架**明文支持三方輸入法**（官方文件寫「面向…三方输入法应用」，
`hdc shell ime -e <bundle>` 明文支持啟用三方輸入法，並有官方範例 App **KikaInput**）。
**技術上可行。**

**真正的限制是治理，不是 API**：

| 限制 | 來源 | 對本專案的影響 |
|---|---|---|
| 基礎訪問模式**禁止網路互動** | 官方「约束与限制」原文 | 雲端詞庫不可行——我們本來就不做，**無影響** |
| 未來將加嚴：獨立沙箱、禁子進程、限 IPC | 同上 | 核心必須 **in-process**——我們的 C ABI 本來就是，**無影響** |
| 部分能力僅系統預設輸入法可用（`12800010`） | API 文件 | 少數進階功能拿不到，**可接受** |
| 簽章／AGC／**側載**／上架資質 | **【需查證】** | **這是真正的未知數** |

**驗證計畫（兩週）**：

1. **先確認 AppGallery 上是否已有第三方中文輸入法**（搜狗／百度／訊飛鴻蒙版）。
   這一題的答案決定一切：若已有且可設為預設 → 商業可行性立即確認；
   若確實沒有 → 先行者機會。
2. 用 DevEco Studio 建最小 `InputMethodExtensionAbility`，實機上被列為可選輸入法
3. ArkTS 寫死小詞表，打出「你好」
4. 確認 NAPI 能否載入自帶的 C ABI 靜態庫

**成功** → M7 立項。**失敗** → 改為「把引擎與詞庫開放給鴻蒙開發者」，不自建外殼。

**風險**：未知（但已從「未知的未知」降級為「已知的四個問題」）。因此**不先進排程**。

詳見 [03-platform-matrix.md](03-platform-matrix.md)。

### M8 · 加值功能（持續）

依「使用者最常抱怨／最常要求」排序，而非依實作難度：

| 優先 | 功能 | 對標自然輸入法 |
|---|---|---|
| 1 | 簡繁轉換（OpenCC） | ⭐ 一鍵切換簡體 |
| 2 | 符號表與標點智慧對應 | ⭐ 內建 48 組符號表 |
| 3 | 常用詞／長句聯想 | ⭐ 長句聯想 |
| 4 | 許氏、倚天 26 鍵 | 支援許氏／倚天 26 |
| 5 | 數字快打（中文數字、千分位、日期） | ⭐ 數字快打 |
| 6 | 英文聯想 | ⭐ 英文聯想 |
| 7 | 破音字優先序（教育部《一字多音審訂表》） | 內部選字品質 |

**明確不做**：雲端同步（隱私風險與營運成本不值得，改為檔案匯出匯入）、
帳號系統、任何形式的線上啟用驗證。**這些正是競品客服負擔的來源（見 [01](01-competitive-analysis.md) 第 5 節）。**

## 這個專案可能失敗的方式

誠實列出，因為這比樂觀的排程有用：

1. **Windows TSF 吃掉所有時間**（機率：中）。對策：先出可攜版驗證需求，TSF 後置。
2. **選字品質不如自然輸入法，使用者試用後離開**（機率：中—高）。
   對策：M2 的學習能力與 bigram 模型是**必要**而非加分；並且要建立可量化的評測
   （首選正確率、KSPC），否則無法知道自己是進步還是退步。
3. **HarmonyOS 不允許第三方輸入法**（機率：未知）。對策：見 M7 的退路。
4. **只有一個人做**（機率：高）。對策：里程碑切得夠小，每個里程碑結束都有一個
   「可交付、可展示、可停止」的狀態。M0 與 M1 已經符合這個標準。
