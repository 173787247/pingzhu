# 06 · 引擎設計

> 對應程式碼：`engine/src/`。所有數字都是在本倉庫實測得到的，不是估計值。

## 流程總覽

```
按鍵 "j" "i" "3" "9" "4" "s" "u" "3"
   │
   │ KeyBoardLayout（大千式）
   ▼
組件流  ㄨ ㄛ ˇ ㄞ ˋ ㄋ ㄧ ˇ
   │
   │ 音節切分（列舉所有合法切法）
   ▼
候選切分  [ㄨㄛˇ][ㄞˋ][ㄋㄧˇ]   ← 我愛你
          [ㄨㄛˇ][ㄋㄞˋ][ㄧˇ]   ← 我奈以（同樣合法！）
   │
   │ ReadingGrid + Viterbi（用語言模型聯合評分每個切分）
   ▼
最佳解    ㄨㄛˇ-ㄞˋ-ㄋㄧˇ → 我愛你（score -5.40）
```

## 為什麼切分必須和選字一起做

這是一個很容易做錯的地方。傳統做法是兩段式：

1. **切分**：把按鍵流切成音節
2. **轉換**：把音節序列轉成詞

問題在於第一步就必須做決定，而 `ji394su3` 的兩種切分在第一階段**完全無法區分**：

| 切分 | 注音 | 是否合法 | 結果 |
|---|---|---|---|
| A | `ㄨㄛˇ-ㄞˋ-ㄋㄧˇ` | ✅ | 我愛你 |
| B | `ㄨㄛˇ-ㄋㄞˋ-ㄧˇ` | ✅ | 我奈以 |

兩者都是合法音節序列（`ㄋㄞˋ` 是「奈」的讀音，`ㄧˇ` 是「以」的讀音）。
切分器沒有任何資訊可以排除 B。

因此本引擎把切分視為**假設**而非**結論**：列舉所有合法切分，
每一個都送進讀字格做完整解碼，最後比較總分。

實測結果（`engine/test/engine.test.ts`）：

```
ji394su3  →  ㄨㄛˇ ㄞˋ ㄋㄧˇ  →  我愛你  (score -5.40)
```

語言模型在這裡的關鍵作用：`我愛你` 是一個詞條，分數 -5.398；
若逐字解，`我` + `愛` + `你` 的對數機率相加約 -12。
**多字詞的機率天然高於其組成字之和**，所以正確答案勝出。

## 音節切分演算法

```
walk(pos):
    if pos == len(keys): 記錄一個完整切分
    for len in 1..4:                      # 一個音節最多 4 個組件
        for chunk in chunkOptions(pos, len):
            syllable = composeSyllable(chunk)
            if syllable 不在合法音節集: continue
            if not isWellFormedComponents(chunk): continue
            if not isCanonicalComponentOrder(chunk): continue
            walk(pos + len)
    if 無法前進 and pos > 0: 記錄一個「部分切分」
```

四個約束：

1. **同類組件不可共存**：一個音節不能有兩個聲母（`composeSyllable` 回傳 null）。
2. **必須是合法音節**：合法音節集**從資料推導**（`data/bopomofo-lm.tsv` 中出現過的讀音，1,413 個），
   而不是手寫表格。手寫表格會漏掉罕用音，且無法隨詞庫更新。
3. **必須「打得完」**：見下一節。
4. **按鍵順序必須合法**：見下下節——這一條是修掉一個嚴重缺陷的關鍵。

### 「打完了沒」的判斷

這決定了打字中途會不會亂出字。規則：

| 情況 | 判定 | 例子 |
|---|---|---|
| 有韻母 | 完整 | `ㄋㄧˇ`、`ㄏㄠˇ` |
| 只有介音 | 完整 | `ㄧ`（一）、`ㄨ`（五）、`ㄩ`（魚）、`ㄏㄨ`（呼） |
| 只有聲母，且是 ㄓㄔㄕㄖㄗㄘㄙ | 完整 | `ㄔ`（吃）、`ㄕ`（詩）、`ㄙ`（思） |
| 只有聲母，其他 | **未完成** | `ㄏ` → 還在打 |
| 只有聲調 | 未完成 | — |

最後一條特別重要：詞庫裡**確實有**「單獨的注音符號」詞條（`ㄅ`、`ㄏ`、`ˇ` 本身可以當字元打出來），
所以合法音節集會誤判 `ㄏ` 是完整音節。良構性檢查把它們排除在自動切分之外。

### 按鍵順序必須合法（一個嚴重缺陷的修復）

`composeSyllable` 是**按類別合併**的：它把一組組件組成一個音節，但不檢查使用者的按鍵順序。
這聽起來無害，實際上讓引擎讀出使用者根本沒打的音：

| 按鍵 | 使用者想打 | 引擎曾經讀成 | 為什麼 |
|---|---|---|---|
| `jptjp6` | `ㄨㄣ-ㄔㄨㄣˊ`（溫純） | `ㄔㄨㄣ-ㄨㄣˊ` | 區塊 `[ㄨ ㄣ ㄔ]` 被組成 `ㄔㄨㄣ`——ㄔ 跳到了 ㄨㄣ 前面 |
| `j0420` | `ㄨㄢˋ-ㄉㄢ`（萬丹） | `ㄨㄢ-ㄉㄢˋ` | 區塊 `[ˋ ㄉ ㄢ]` 被組成 `ㄉㄢˋ`——聲調跑到了下一個音節 |

第二個案例的後果特別嚴重：**「萬丹」這個詞在候選視窗裡完全不存在**，
因為引擎把它切成了完全不同的音節序列，而候選只在「選定的切分」裡找詞。

修法是要求區塊內的類別次序**嚴格遞增**（聲母 → 介音 → 韻母 → 聲調）。
唯一的例外是 `˙`（輕聲）：台灣的書寫慣例是寫在音節前面（`˙ㄉㄜ`），
所以允許它出現在區塊首位。

修復效果（5,000 樣本）：

| 指標 | 修復前 | 修復後 |
|---|---|---|
| top-1 準確率 | 89.44% | **90.38%** |
| 詞輸給拆解 | 52 | **1** |
| 候選完全選不到 | 52 | **1** |
| 每例解碼 | 619 µs | **241 µs** |

最後一項是意外收穫：不合法的切分本來就不該被列舉，少列舉等於少做白工。

### 部分的切分

若整個緩衝區沒有任何完整切分，退回到「消耗按鍵數最多」的部分切分，
剩餘按鍵顯示為 pending。這讓「打到一半」是一個**正常狀態**而非錯誤狀態。

## 讀字格（ReadingGrid）與 Viterbi

把音節排成一列，對每一個連續區間找出所有詞庫詞條鋪上去，形成一個有向無環圖：

```
音節:      ㄨㄛˇ      ㄞˋ       ㄋㄧˇ
          ┌────┐
區間1:    │ 我 │
          └────┘
          ┌──────────┐
區間2:    │  我愛    │
          └──────────┘
          ┌────────────────┐
區間3:    │     我愛你     │  ← -5.398
          └────────────────┘
                     ┌────┐
區間1:               │ 愛 │
                     └────┘
```

DP 轉移：

```
best[0] = 0
best[end] = max over nodes ending at end of ( best[node.start] + node.score )
```

節點分數直接使用語言模型的 log10 機率。**沒有額外的權重、沒有調參數**——
這也是為什麼這份實作可以宣稱「模型換掉、行為就跟著換」，而不是「我們調了很多參數」。

找不到任何詞條的音節會插入一個 fallback 節點（分數 -99 再扣 3.0 懲罰），
讓路徑可以通過，同時在候選清單裡標記出來。

### 解開 packed key 是這個專案的關鍵一步

McBopomofo 的語言模型把讀音壓成每個音節兩個 ASCII 字元的緊湊編碼
（例如 `~l` 代表 `ㄩㄥˋ`），可讀性為零，也讓資料無法被其他專案重用。
編碼方式是：把

```
聲母(0..21) + 介音(0..3)×22 + 韻母(0..13)×88 + 聲調(0..4)×1232
```

組成一個 0..6159 的序號，再輸出成 `chr(48 + n % 79)` 與 `chr(48 + (n/79) & 127)`。

`data/build.mjs` 重新實作了這個解碼（依 McBopomofo 公開的位元佈局，
未複製其原始碼），於是 13 萬條資料變成**人類可讀、可 grep、可被任何語言使用**的注音詞庫。
驗證方式是把解碼結果拿去查已知詞條：

```
ㄋㄧˇ-ㄏㄠˇ          你好     →  -5.089  ✅
ㄨㄛˇ-ㄞˋ-ㄋㄧˇ      我愛你   →  -5.398  ✅
ㄩㄥˋ-ㄗㄞˋ          用在     →  -4.597  ✅
```

### 清理規則

| 規則 | 理由 |
|---|---|
| 丟棄 `MACRO@DATE_*` 條目 | 日期／時間巨集由輸入控制器處理，不是詞庫詞（原本會產生 37 字的「詞」） |
| 每個讀音最多保留 100 個候選 | 單音節讀音可達 3,000+ 同音字（`ㄧˋ` 有 3,032 個），會同時拖垮檔案大小與搜尋 |
| 丟棄 `_ctrl_punctuation_*` 等偽條目 | 標點對應不是注音讀音 |

### 獨立交叉驗證

`docs` 與 `research/04` 是兩條互不依賴的推導路徑，結果一致：

| 項目 | 本專案（從 McBopomofo 編譯後資料解碼） | `research/04`（從 `BPMFMappings.txt` 的 506,778 個音節 token 統計） |
|---|---|---|
| 含聲調合法音節 | **1,413** | **1,413** |
| 無聲調音節 | —（未單獨統計） | 429（清理後 408） |
| 單字表 | 26,315 字 | `BPMFBase.txt` 26,535 行 |

1,413 這個數字兩邊完全吻合，而推導方式完全不同（一邊是解開 packed key，一邊是統計原始
詞庫檔），因此可以合理相信合法音節集沒有系統性遺漏。

### 分數裡已經包含長度補償

McBopomofo 產生這些對數機率時用的公式是：

```
freq(k) = log10( 2.7^(len(k)-1) × occ(k) / norm )
```

`2.7^(len(k)-1)` 是**長度補償**——沒有它，長詞的出現次數永遠低於短詞，
分詞器會系統性偏好逐字解。我們的 `bopomofo-lm.tsv` 取用的是這條管線的**輸出**，
所以 `我愛你 -5.398` 這個分數裡已經含了補償，引擎端不需要再乘任何係數。

這也是為什麼 [06 前面的 Viterbi 段落](#讀字格readinggrid與-viterbi) 能說「沒有額外權重、沒有調參數」。

（例如不需要把詞庫預先編譯成 DAWG／FST；若未來移植到記憶體受限的裝置再說）。

## 候選視窗

引擎不需要「猜對」同音詞，只需要在使用者按一兩個鍵之內**把對的字端出來**。
這是台灣輸入法用了幾十年的約定，也是把「同音詞無解」從缺陷變成 UI 問題的關鍵。

| 操作 | 行為 |
|---|---|
| `1`…`9`、`0` | 選目前頁面的第 1…10 個候選 |
| `空白鍵` | 送出組字；候選視窗開啟時翻到下一頁（十個） |
| `←` `→` | 沿著組字緩衝區移動候選游標 |

一頁十個，因為鍵盤上正好有 `1234567890` 十個鍵可以指涉。**空白鍵因此不是組字鍵**
（見 `keyboard.ts`：兩種鍵盤排列都刻意不把空白鍵對應到任何組件）——一聲不需要按鍵，
音節由下一個音節的首鍵或聲調鍵自然關閉。

### 候選排序

三種排序都**按詞頻**，差別只在要不要先分組；每一組內部都是詞頻序。

引擎選錯時（5,000 樣本中的 481 例），正確的字落在哪一頁：

| 排序 | 第 1 頁（1-0） | 第 2 頁 | 第 3 頁 | 完全選不到 |
|---|---|---|---|---|
| **`same-span-first`（預設）** | **99.8%** | 99.8% | 99.8% | 1 |
| `longest-first` | 99.8% | 99.8% | 99.8% | 1 |
| `frequency`（純詞頻） | 55.9% | 87.3% | 95.0% | 1 |

純詞頻排序的問題很具體：**常用單字永遠贏過它自己所屬的罕用詞**。
`ㄔㄨˋ-ㄕㄥ` 的候選是

```
frequency:       1.處  2.觸  3.畜  4.矗  5.畜生  6.絀  7.畜牲 …
same-span-first: 1.畜生  2.畜牲  3.處  4.觸  5.畜  6.矗  7.絀 …
```

使用者打了兩個音節，按 `1` 卻拿到「處」。預設排序把「與引擎自己選的那個詞同跨度的
同音對手」排在最前，其餘按詞頻——這樣既保證了**視窗第一頁一定包含畫面上顯示的那個句子**
（否則 UI 自相矛盾），又在長緩衝區裡不會像 `longest-first` 那樣把一個罕用的整句詞推到最前面。

純詞頻排序保留為選項：它是專案所有者指定的慣例，而它的代價應該被**量測**而不是被假設掉。

## 個人化：使用者詞庫與學習

語料庫再大，`遺臣` 與 `一陳` 的讀音還是完全相同。唯一能分開它們的，是**知道這個使用者打的是哪一個**。

### 設計

學習以「讀音 → 詞」為單位。使用者的知識以 **log10 加成**疊加在語言模型分數之上：

```
final = lmScore + userBonus
```

每個 +1.0 代表「比模型原本認為的機率高十倍」。加成有兩層：

1. **不會衰減到零的地板**。每一級都在 1.5 以上。使用者刻意選擇的字應該持續贏過模型在該讀音的預設
   ——libchewing 也是這個立場（它的使用者詞頻存在百萬級，就是為了讓 `max(內建, 使用者)` 永遠解析到使用者的詞）。
   一個會衰減到 0 的加成，意思等同「一個月後我們就忘記你的更正」，而那並不是「教會一個詞」的意思。
2. **在 `firstSeen` 的視窗內保留最高級**：今天教過的詞在 `recentDays` 內維持最高加成，
   即使沒有立刻再用一次——一次更正不該在一週後悄悄掉隊。

### 只有「明確選擇」才算學習

`commit()` 預設**不**記錄（`learnFromCommit: false`）。

這是一個刻意的決定，不是疏漏：當使用者接受引擎自動選出的同音詞時，他可能是在認可它，
也可能根本沒注意到。從那裡學習會**固化使用者最不容易察覺的錯誤**。
明確的選擇（`choose()` / `chooseAt()` / `selectCandidate()`）是無疑的意圖證據，一律學習。

| 其中詞輸給拆解 | 1 | 詞庫有這個詞，卻輸給逐字拼 |
| KSPC | 2.986 | 每產生一個字要按幾個鍵 |
| 每例解碼 | 241.5 µs | 含測試框架開銷 |

### 剩下的 481 例是什麼

**480 例是同音詞平手**，1 例是詞輸給拆解：

```
ㄔㄨˋ-ㄕㄥ       want 畜牲   got 畜生
ㄕㄣ-ㄔˋ        want 申飭   got 申斥
ㄐㄧㄣˋ-ㄌㄨˋ    want 近路   got 進路
ㄧㄢˇ-ㄙㄜˋ     want 演色   got 眼色
ㄐㄧ-ㄡˇ        want 奇偶   got 九      ← 連切分都不同，見「已知限制」
```

讀音完全正確，是**詞彙選擇**問題。5,000 個樣本中**沒有任何一次真正的解碼失敗**
（`usedFallback` 從未被觸發）。

**這決定了路線圖的優先序**：把準確率往上推有兩條路——bigram／上下文模型
（libchewing-data v4 有注音專用 bigram，見 [04](04-data-and-licensing.md)），
以及**讓使用者自己選**（`bench-learn.mjs` 實測：教 492 個詞之後 top-1 達 99.54%）。
詞庫再大也解決不了同音詞，但一頁候選可以。

### `reading accuracy` 是怎麼算的（為何它可證明）

不是拿輸出字串去詞庫裡比對（那會誤判：`負色` 是 `ㄈㄨˋ`+`ㄙㄜˋ` 兩個單字節點拼出來的，
不是一條詞庫詞條，但它確實讀作 `ㄈㄨˋ-ㄙㄜˋ`）。而是用引擎自己暴露的
`usedFallback`：

> 若最佳路徑上沒有任何 fallback 節點，則路徑上每一個節點都是「讀音與其覆蓋音節相符」的
> 詞庫詞條，因此輸出**必然**讀得回輸入。這是結構上的保證，不是抽樣估計。

### 這個評測不能證明什麼

樣本取自語言模型本身，模型既是答案卷也是解題者。所以：

- ✅ 可以說：解碼在結構上正確、沒有回歸
- ❌ 不能說：贏過自然輸入法、90.38% 是真實首選率

真實數字需要一份「使用者實際打字 + 意圖標註」的語料，目前不存在。
建立這份語料本身就是一件該做的事（見 [05](05-roadmap.md)）。

**尚未實作**：簡繁轉換、符號表、聯想詞、快捷輸入、數字快打、雲端同步（M8）。

## 已知限制

1. **許氏、倚天 26 鍵未支援。** 這兩種排列需要**有狀態**的編輯器：大量鍵位取決於音節
   已輸入的內容（例如許氏把「ㄑ」實作為 `v`(ㄔ) + ㄧ/ㄩ 的自動轉換，不知道這條規則
   就永遠打不出「去 ㄑㄩˋ」）。`research/04` §2.2.5 已從 libchewing 的 Rust 原始碼
   還原出完整規則，但實作需要改動切分層。
   `engine/src/keyboard.ts` 的 `PLANNED_LAYOUTS` 明列待補。
   目前的大千式覆蓋 >95% 台灣使用者。
2. **候選視窗只在「選定的那個切分」裡找詞。** 這是目前最實在的功能缺口，有具體案例：

   ```
   按鍵 ru.3    ㄐㄧ-ㄡˇ（奇偶）與 ㄐㄧㄡˇ（九）的按鍵完全相同
   引擎選了高頻的 ㄐㄧㄡˇ → 候選是 九 久 酒 糾 灸 玖
   「奇偶」永遠不會出現，因為它需要另一個切分
   ```

   修法是把前 K 個切分的候選合併進同一個視窗。5,000 樣本中觸發 1 次（0.02%），
   不是當務之急，但這是真實使用者會撞到的牆。

3. **學習會全域影響路徑。** 學習以「讀音 → 詞」為單位，但解碼是全域最佳化，
   所以教一個詞可能改變另一個組字緩衝區的切分。實測（教學 492 個詞之後）5,000 例中 1 例：

   ```
   教過 ㄧㄡˊ-ㄗ 的「郵資」之後
   按鍵 u.6yj/（ㄧㄡˊ-ㄗㄨㄥ）變成 郵資|翁，而不是 遊蹤
   ```

   這是全域解碼的固有性質，不是實作錯誤；根治需要「切分感知的學習」。

4. **沒有 bigram。** 目前只用詞條自身的對數機率，沒有「前一個詞影響下一個詞」的脈絡模型。
   libchewing-data v4 有注音專用 bigram（見 [04](04-data-and-licensing.md)），是後續升級點。

5. **沒有破音字優先序表。** 破音字目前完全交由語言模型在切分時解決；
   教育部《一字多音審訂表》的優先序（`research/04` §3.5）尚未匯入。

6. **詞庫只涵蓋繁體。** 簡體輸出需接 OpenCC（Apache-2.0）。

7. **學習的加成常數是設計選擇，不是推導出來的。** `UserDictionaryOptions` 的
   `bonusNew` / `bonusRecent` / `bonusMid` / `bonusOld` 是「合理但未經真實使用者驗證」的值。
   要調它們需要真實打字資料，目前沒有。
