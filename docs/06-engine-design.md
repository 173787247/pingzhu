# 06 · 引擎设计

> 对应程式码：`engine/src/`。所有数字都是在本仓库实测得到的，不是估计值。

## 流程总览

```
按鍵 "j" "i" "3" "9" "4" "s" "u" "3"
   │
   │ KeyBoardLayout（大千式）
   ▼
組件流  ㄨ ㄛ ˇ ㄞ ˋ ㄋ ㄧ ˇ
   │
   │ 音節切分（列舉所有合法切法）
   ▼
候選切分  [ㄨㄛˇ][ㄞˋ][ㄋㄧˇ]   ← 我愛你
          [ㄨㄛˇ][ㄋㄞˋ][ㄧˇ]   ← 我奈以（同樣合法！）
   │
   │ ReadingGrid + Viterbi（用語言模型聯合評分每個切分）
   ▼
最佳解    ㄨㄛˇ-ㄞˋ-ㄋㄧˇ → 我愛你（score -5.40）
```

## 为什么切分必须和选字一起做

这是一个很容易做错的地方。传统做法是两段式：

1. **切分**：把按键流切成音节
2. **转换**：把音节序列转成词

问题在于第一步就必须做决定，而 `ji394su3` 的两种切分在第一阶段**完全无法区分**：

| 切分 | 注音 | 是否合法 | 结果 |
|---|---|---|---|
| A | `ㄨㄛˇ-ㄞˋ-ㄋㄧˇ` | ✅ | 我爱你 |
| B | `ㄨㄛˇ-ㄋㄞˋ-ㄧˇ` | ✅ | 我奈以 |

两者都是合法音节序列（`ㄋㄞˋ` 是「奈」的读音，`ㄧˇ` 是「以」的读音）。
切分器没有任何资讯可以排除 B。

因此本引擎把切分视为**假设**而非**结论**：列举所有合法切分，
每一个都送进读字格做完整解码，最后比较总分。

实测结果（`engine/test/engine.test.ts`）：

```
ji394su3  →  ㄨㄛˇ ㄞˋ ㄋㄧˇ  →  我愛你  (score -5.40)
```

语言模型在这里的关键作用：`我愛你` 是一个词条，分数 -5.398；
若逐字解，`我` + `愛` + `你` 的对数机率相加约 -12。
**多字词的机率天然高于其组成字之和**，所以正确答案胜出。

## 音节切分演算法

```
walk(pos):
    if pos == len(keys): 記錄一個完整切分
    for len in 1..4:                      # 一個音節最多 4 個組件
        for chunk in chunkOptions(pos, len):
            syllable = composeSyllable(chunk)
            if syllable 不在合法音節集: continue
            if not isWellFormedComponents(chunk): continue
            if not isCanonicalComponentOrder(chunk): continue
            walk(pos + len)
    if 無法前進 and pos > 0: 記錄一個「部分切分」
```

四个约束：

1. **同类组件不可共存**：一个音节不能有两个声母（`composeSyllable` 回传 null）。
2. **必须是合法音节**：合法音节集**从资料推导**（`data/bopomofo-lm.tsv` 中出现过的读音，1,413 个），
   而不是手写表格。手写表格会漏掉罕用音，且无法随词库更新。
3. **必须「打得完」**：见下一节。
4. **按键顺序必须合法**：见下下节——这一条是修掉一个严重缺陷的关键。

### 「打完了没」的判断

这决定了打字中途会不会乱出字。规则：

| 情况 | 判定 | 例子 |
|---|---|---|
| 有韵母 | 完整 | `ㄋㄧˇ`、`ㄏㄠˇ` |
| 只有介音 | 完整 | `ㄧ`（一）、`ㄨ`（五）、`ㄩ`（鱼）、`ㄏㄨ`（呼） |
| 只有声母，且是 ㄓㄔㄕㄖㄗㄘㄙ | 完整 | `ㄔ`（吃）、`ㄕ`（诗）、`ㄙ`（思） |
| 只有声母，其他 | **未完成** | `ㄏ` → 还在打 |
| 只有声调 | 未完成 | — |

最后一条特别重要：词库里**确实有**「单独的注音符号」词条（`ㄅ`、`ㄏ`、`ˇ` 本身可以当字元打出来），
所以合法音节集会误判 `ㄏ` 是完整音节。良构性检查把它们排除在自动切分之外。

### 按键顺序必须合法（一个严重缺陷的修复）

`composeSyllable` 是**按类别合并**的：它把一组组件组成一个音节，但不检查使用者的按键顺序。
这听起来无害，实际上让引擎读出使用者根本没打的音：

| 按键 | 使用者想打 | 引擎曾经读成 | 为什么 |
|---|---|---|---|
| `jptjp6` | `ㄨㄣ-ㄔㄨㄣˊ`（温纯） | `ㄔㄨㄣ-ㄨㄣˊ` | 区块 `[ㄨ ㄣ ㄔ]` 被组成 `ㄔㄨㄣ`——ㄔ 跳到了 ㄨㄣ 前面 |
| `j0420` | `ㄨㄢˋ-ㄉㄢ`（万丹） | `ㄨㄢ-ㄉㄢˋ` | 区块 `[ˋ ㄉ ㄢ]` 被组成 `ㄉㄢˋ`——声调跑到了下一个音节 |

第二个案例的后果特别严重：**「万丹」这个词在候选视窗里完全不存在**，
因为引擎把它切成了完全不同的音节序列，而候选只在「选定的切分」里找词。

修法是要求区块内的类别次序**严格递增**（声母 → 介音 → 韵母 → 声调）。
唯一的例外是 `˙`（轻声）：台湾的书写惯例是写在音节前面（`˙ㄉㄜ`），
所以允许它出现在区块首位。

修复效果（5,000 样本）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| top-1 准确率 | 89.44% | **90.38%** |
| 词输给拆解 | 52 | **1** |
| 候选完全选不到 | 52 | **1** |
| 每例解码 | 619 µs | **241 µs** |

最后一项是意外收获：不合法的切分本来就不该被列举，少列举等于少做白工。

### 部分的切分

若整个缓冲区没有任何完整切分，退回到「消耗按键数最多」的部分切分，
剩余按键显示为 pending。这让「打到一半」是一个**正常状态**而非错误状态。

## 读字格（ReadingGrid）与 Viterbi

把音节排成一列，对每一个连续区间找出所有词库词条铺上去，形成一个有向无环图：

```
音節:      ㄨㄛˇ      ㄞˋ       ㄋㄧˇ
          ┌────┐
區間1:    │ 我 │
          └────┘
          ┌──────────┐
區間2:    │  我愛    │
          └──────────┘
          ┌────────────────┐
區間3:    │     我愛你     │  ← -5.398
          └────────────────┘
                     ┌────┐
區間1:               │ 愛 │
                     └────┘
```

DP 转移：

```
best[0] = 0
best[end] = max over nodes ending at end of ( best[node.start] + node.score )
```

节点分数直接使用语言模型的 log10 机率。**没有额外的权重、没有调参数**——
这也是为什么这份实作可以宣称「模型换掉、行为就跟著换」，而不是「我们调了很多参数」。

找不到任何词条的音节会插入一个 fallback 节点（分数 -99 再扣 3.0 惩罚），
让路径可以通过，同时在候选清单里标记出来。


### 解开 packed key 是这个专案的关键一步

McBopomofo 的语言模型把读音压成每个音节两个 ASCII 字元的紧凑编码
（例如 `~l` 代表 `ㄩㄥˋ`），可读性为零，也让资料无法被其他专案重用。
编码方式是：把

```
聲母(0..21) + 介音(0..3)×22 + 韻母(0..13)×88 + 聲調(0..4)×1232
```

组成一个 0..6159 的序号，再输出成 `chr(48 + n % 79)` 与 `chr(48 + (n/79) & 127)`。

`data/build.mjs` 重新实作了这个解码（依 McBopomofo 公开的位元布局，
未复制其原始码），于是 13 万条资料变成**人类可读、可 grep、可被任何语言使用**的注音词库。
验证方式是把解码结果拿去查已知词条：

```
ㄋㄧˇ-ㄏㄠˇ          你好     →  -5.089  ✅
ㄨㄛˇ-ㄞˋ-ㄋㄧˇ      我愛你   →  -5.398  ✅
ㄩㄥˋ-ㄗㄞˋ          用在     →  -4.597  ✅
```

### 清理规则

| 规则 | 理由 |
|---|---|
| 丢弃 `MACRO@DATE_*` 条目 | 日期／时间巨集由输入控制器处理，不是词库词（原本会产生 37 字的「词」） |
| 每个读音最多保留 100 个候选 | 单音节读音可达 3,000+ 同音字（`ㄧˋ` 有 3,032 个），会同时拖垮档案大小与搜寻 |
| 丢弃 `_ctrl_punctuation_*` 等伪条目 | 标点对应不是注音读音 |

### 独立交叉验证

`docs` 与 `research/04` 是两条互不依赖的推导路径，结果一致：

| 项目 | 本专案（从 McBopomofo 编译后资料解码） | `research/04`（从 `BPMFMappings.txt` 的 506,778 个音节 token 统计） |
|---|---|---|
| 含声调合法音节 | **1,413** | **1,413** |
| 无声调音节 | —（未单独统计） | 429（清理后 408） |
| 单字表 | 26,315 字 | `BPMFBase.txt` 26,535 行 |

1,413 这个数字两边完全吻合，而推导方式完全不同（一边是解开 packed key，一边是统计原始
词库档），因此可以合理相信合法音节集没有系统性遗漏。

### 分数里已经包含长度补偿

McBopomofo 产生这些对数机率时用的公式是：

```
freq(k) = log10( 2.7^(len(k)-1) × occ(k) / norm )
```

`2.7^(len(k)-1)` 是**长度补偿**——没有它，长词的出现次数永远低于短词，
分词器会系统性偏好逐字解。我们的 `bopomofo-lm.tsv` 取用的是这条管线的**输出**，
所以 `我愛你 -5.398` 这个分数里已经含了补偿，引擎端不需要再乘任何系数。

这也是为什么 [06 前面的 Viterbi 段落](#读字格readinggrid与-viterbi) 能说「没有额外权重、没有调参数」。

（例如不需要把词库预先编译成 DAWG／FST；若未来移植到记忆体受限的装置再说）。

## 候选视窗

引擎不需要「猜对」同音词，只需要在使用者按一两个键之内**把对的字端出来**。
这是台湾输入法用了几十年的约定，也是把「同音词无解」从缺陷变成 UI 问题的关键。

| 操作 | 行为 |
|---|---|
| `1`…`9`、`0` | 选目前页面的第 1…10 个候选（**只在视窗开启时**；否则是注音键） |
| `空白鍵` | 第一次：开启视窗；已开启：送出目前的首选；没有候选：送出 |
| `↓` | 开启视窗；已开启：翻到下一页（十个） |
| `←` `→` | 沿著组字缓冲区移动候选游标 |

一页十个，因为键盘上正好有 `1234567890` 十个键可以指涉。**空白键因此不是组字键**
（见 `keyboard.ts`：两种键盘排列都刻意不把空白键对应到任何组件）——一声不需要按键，
音节由下一个音节的首键或声调键自然关闭。

**★ 空白键为什么是「先开、再送」而不是「送出、或翻页」（2026-10 改）**

原本是「没开窗就送出，开了窗就翻页」。两个问题：

1. **第二个候选到不了** —— 想选 `5j4u4`（ㄓㄨˋ-ㄧˋ）候选页第 2 个「助益」的人，
   按空白只得到「注意」。他必须**事先知道**要按 `↓` 才看得到那张单子。
2. **最常按的键去翻页** —— 空白是大家拿来「接受」的键，让它捲一张没人要求捲的
   清单，是四个外壳都同意要避免的事（见 `windows/src/router.cpp` 的注释）。

改成「先开、再送」之后，空白**仍然以接受收尾**，只是不在第一次按下时。

**已知代价**：最高频的动作——打完就送出——从一次空白变成两次。这是刻意的取舍，
记在这里以便日后有人想再改时知道自己站在哪里。

**★ 路由规则的测试覆盖有一个已记录的缺口**：`tools/routing-vectors.tsv` 的用意是
「新增规则时改这里，四边一起红」，但目前**只有 macOS 的测试真的读它**
（`macos/Tests/Router/main.swift`）。Windows 与 Android 是各自写死的断言，
所以改了一条规则之后，另外两边**不会自己红**——2026-10 这次改动就是这样，
两边的断言都是手动跟着改的。修法是让那两个测试也读同一份向量。

### 候选排序

三种排序都**按词频**，差别只在要不要先分组；每一组内部都是词频序。

引擎选错时（5,000 样本中的 481 例），正确的字落在哪一页：

| 排序 | 第 1 页（1-0） | 第 2 页 | 第 3 页 | 完全选不到 |
|---|---|---|---|---|
| **`same-span-first`（预设）** | **99.8%** | 99.8% | 99.8% | 1 |
| `longest-first` | 99.8% | 99.8% | 99.8% | 1 |
| `frequency`（纯词频） | 55.9% | 87.3% | 95.0% | 1 |

纯词频排序的问题很具体：**常用单字永远赢过它自己所属的罕用词**。
`ㄔㄨˋ-ㄕㄥ` 的候选是

```
frequency:       1.處  2.觸  3.畜  4.矗  5.畜生  6.絀  7.畜牲 …
same-span-first: 1.畜生  2.畜牲  3.處  4.觸  5.畜  6.矗  7.絀 …
```

使用者打了两个音节，按 `1` 却拿到「处」。预设排序把「与引擎自己选的那个词同跨度的
同音对手」排在最前，其余按词频——这样既保证了**视窗第一页一定包含画面上显示的那个句子**
（否则 UI 自相矛盾），又在长缓冲区里不会像 `longest-first` 那样把一个罕用的整句词推到最前面。

纯词频排序保留为选项：它是专案所有者指定的惯例，而它的代价应该被**量测**而不是被假设掉。

## 个人化：使用者词库与学习

语料库再大，`遺臣` 与 `一陳` 的读音还是完全相同。唯一能分开它们的，是**知道这个使用者打的是哪一个**。

### 设计

学习以「读音 → 词」为单位。使用者的知识以 **log10 加成**叠加在语言模型分数之上：

```
final = lmScore + userBonus
```

每个 +1.0 代表「比模型原本认为的机率高十倍」。加成有两层：

1. **不会衰减到零的地板**。每一级都在 1.5 以上。使用者刻意选择的字应该持续赢过模型在该读音的预设
   ——libchewing 也是这个立场（它的使用者词频存在百万级，就是为了让 `max(內建, 使用者)` 永远解析到使用者的词）。
   一个会衰减到 0 的加成，意思等同「一个月后我们就忘记你的更正」，而那并不是「教会一个词」的意思。
2. **在 `firstSeen` 的视窗内保留最高级**：今天教过的词在 `recentDays` 内维持最高加成，
   即使没有立刻再用一次——一次更正不该在一周后悄悄掉队。

### 只有「明确选择」才算学习

`commit()` 预设**不**记录（`learnFromCommit: false`）。

这是一个刻意的决定，不是疏漏：当使用者接受引擎自动选出的同音词时，他可能是在认可它，
也可能根本没注意到。从那里学习会**固化使用者最不容易察觉的错误**。
明确的选择（`choose()` / `chooseAt()` / `selectCandidate()`）是无疑的意图证据，一律学习。

### 实测（5,000 样本，模拟「使用者只更正一次」）

| 指标 | 学习前 | 学习后 |
|---|---|---|
| top-1 准确率 | 90.38% | **99.54%** |
| 读音准确率 | 100.00% | 100.00% |
| 同音词平手 | 480 | 21 |
| 词输给拆解 | 1 | 2 |

- 修好 **464** 例

  使用者不可能两个都要），**1 例是真实副作用**（见下方限制）

## 评测（`engine/bench.mjs`）

单元测试钉住个案，评测量的是整体品质。5,000 个取样读音的结果：

| 指标 | 数值 | 意义 |
|---|---|---|
| top-1 exact accuracy | **83.22%** | 自动选出的词与取样词完全相同 |
| reading accuracy | **100.00%** | 输出「读得回」输入的音 |
| 其中同音词平手 | 480 | 读音相同但用字不同 |
| 其中词输给拆解 | 1 | 词库有这个词，却输给逐字拼 |
| KSPC | 2.986 | 每产生一个字要按几个键 |
| 每例解码 | 241.5 µs | 含测试框架开销 |

### 剩下的 481 例是什么

**480 例是同音词平手**，1 例是词输给拆解：

```
ㄔㄨˋ-ㄕㄥ       want 畜牲   got 畜生
ㄕㄣ-ㄔˋ        want 申飭   got 申斥
ㄐㄧㄣˋ-ㄌㄨˋ    want 近路   got 進路
ㄧㄢˇ-ㄙㄜˋ     want 演色   got 眼色
ㄐㄧ-ㄡˇ        want 奇偶   got 九      ← 連切分都不同，見「已知限制」
```

读音完全正确，是**词汇选择**问题。5,000 个样本中**没有任何一次真正的解码失败**
（`usedFallback` 从未被触发）。

**这决定了路线图的优先序**：把准确率往上推有两条路——bigram／上下文模型
（libchewing-data v4 有注音专用 bigram，见 [04](04-data-and-licensing.md)），
以及**让使用者自己选**（`bench-learn.mjs` 实测：教 492 个词之后 top-1 达 99.54%）。
词库再大也解决不了同音词，但一页候选可以。

### `reading accuracy` 是怎么算的（为何它可证明）

不是拿输出字串去词库里比对（那会误判：`負色` 是 `ㄈㄨˋ`+`ㄙㄜˋ` 两个单字节点拼出来的，
不是一条词库词条，但它确实读作 `ㄈㄨˋ-ㄙㄜˋ`）。而是用引擎自己暴露的
`usedFallback`：

> 若最佳路径上没有任何 fallback 节点，则路径上每一个节点都是「读音与其覆盖音节相符」的
> 词库词条，因此输出**必然**读得回输入。这是结构上的保证，不是抽样估计。

### 这个评测不能证明什么

样本取自语言模型本身，模型既是答案卷也是解题者。所以：

- ✅ 可以说：解码在结构上正确、没有回归
- ❌ 不能说：赢过自然输入法、90.38% 是真实首选率

真实数字需要一份「使用者实际打字 + 意图标注」的语料，目前不存在。
建立这份语料本身就是一件该做的事（见 [05](05-roadmap.md)）。

**已实作**：简繁转换（[09](09-zhuyin-vs-pinyin.md) 的对照表，三种切换方式）。

**尚未实作**：符号表、联想词、快捷输入、数字快打、云端同步（M8）。

## 已知限制

1. **许氏、倚天 26 键未支援。** 这两种排列需要**有状态**的编辑器：大量键位取决于音节
   已输入的内容（例如许氏把「ㄑ」实作为 `v`(ㄔ) + ㄧ/ㄩ 的自动转换，不知道这条规则
   就永远打不出「去 ㄑㄩˋ」）。`research/04` §2.2.5 已从 libchewing 的 Rust 原始码
   还原出完整规则，但实作需要改动切分层。
   `engine/src/keyboard.ts` 的 `PLANNED_LAYOUTS` 明列待补。
   目前的大千式覆盖 >95% 台湾使用者。
2. **候选视窗只在「选定的那个切分」里找词。** 这是目前最实在的功能缺口，有具体案例：

   ```
   按鍵 ru.3    ㄐㄧ-ㄡˇ（奇偶）與 ㄐㄧㄡˇ（九）的按鍵完全相同
   引擎選了高頻的 ㄐㄧㄡˇ → 候選是 九 久 酒 糾 灸 玖
   「奇偶」永遠不會出現，因為它需要另一個切分
   ```

   修法是把前 K 个切分的候选合并进同一个视窗。5,000 样本中触发 1 次（0.02%），
   不是当务之急，但这是真实使用者会撞到的墙。

3. **学习会全域影响路径。** 学习以「读音 → 词」为单位，但解码是全域最佳化，
   所以教一个词可能改变另一个组字缓冲区的切分。实测（教学 492 个词之后）5,000 例中 1 例：

   ```
   教過 ㄧㄡˊ-ㄗ 的「郵資」之後
   按鍵 u.6yj/（ㄧㄡˊ-ㄗㄨㄥ）變成 郵資|翁，而不是 遊蹤
   ```

   这是全域解码的固有性质，不是实作错误；根治需要「切分感知的学习」。

4. **没有 bigram。** 目前只用词条自身的对数机率，没有「前一个词影响下一个词」的脉络模型。
   libchewing-data v4 有注音专用 bigram（见 [04](04-data-and-licensing.md)），是后续升级点。

5. **没有破音字优先序表。** 破音字目前完全交由语言模型在切分时解决；
   教育部《一字多音审订表》的优先序（`research/04` §3.5）尚未汇入。

6. **词库只涵盖繁体。** 简体输出需接 OpenCC（Apache-2.0）。

7. **学习的加成常数是设计选择，不是推导出来的。** `UserDictionaryOptions` 的
   `bonusNew` / `bonusRecent` / `bonusMid` / `bonusOld` 是「合理但未经真实使用者验证」的值。
   要调它们需要真实打字资料，目前没有。
