# 08 · 資料層可以自建

> 這份文件要推翻 [04](04-data-and-licensing.md) 可能給人的錯誤印象。
> 04 花了很多篇幅分析授權，容易讀成「這個專案被上游資料綁住」。
> **事實相反：資料層既不是依賴，也不是護城河。**

## 核心論點

注音輸入法需要的資料，本質上是四張表：

| 表 | 內容 | 規模量級 |
|---|---|---|
| 讀音表 | 漢字 → 注音（含破音字） | 10⁴–10⁵ |
| 詞庫 | 詞 → 讀音 | 10⁵ |
| 詞頻表 | 詞 → 出現次數／機率 | 10⁵ |
| 對照表 | 繁↔簡、注音↔拼音 | 10³–10⁴ |

**這四張表都可以自建，而且用的都是寬鬆授權或事實性資料。**
上游開放資料（McBopomofo、libchewing-data）只是**省時間**，不是**能不能做**的前提。

這件事的戰略意義：**任何一個上游改變授權、停止維護、或消失，本專案都不會死。**

## 一、簡繁轉換表：可以直接從 Unicode 長出來

[Unicode Unihan 資料庫](https://www.unicode.org/Public/UCD/latest/ucd/Unihan.zip)（**Unicode License，
寬鬆、可商用**）直接提供：

| 欄位 | 筆數 | 用途 |
|---|---|---|
| `kSimplifiedVariant` | **7,291** | 繁 → 簡 |
| `kTraditionalVariant` | **6,840** | 簡 → 繁 |
| `kSemanticVariant` | 3,563 | 語意異體 |
| `kZVariant` | 159 | 異體字 |

**本倉庫實測**（下載 Unihan.zip 後統計欄位分布）：

```
U+346E  kSimplifiedVariant    U+2B748
U+3437  kTraditionalVariant   U+508C
```

所以「簡繁轉換」有兩條獨立的路：

1. **OpenCC（Apache-2.0）**——成熟、處理了一對多與詞組層級規則，**建議直接用這個**
2. **Unihan 自建**——一萬四千條字級對照，作為 fallback 或交叉驗證

> ⚠️ 字級對照不足以處理一對多（例如「干」→「乾／幹／干」需要詞組規則）。
> 自建版本要能用，必須額外處理詞組層級的例外表。這是 OpenCC 存在的理由。

## 二、讀音表與破音字：Unihan 也給了

| 欄位 | 筆數 | 說明 |
|---|---|---|
| `kMandarin` | **44,355** | 漢語拼音讀音（含調號） |
| `kHanyuPinyin` | 34,130 | 漢語拼音（多讀音） |
| `kTGHZ2013` | 8,105 | 《通用規範漢字表》讀音 |
| `kXHC1983` | 11,072 | 《現代漢語詞典》讀音 |
| **`kHanyuPinlu`** | **3,799** | **讀音頻次**，例如 `U+4E00 kHanyuPinlu yī(32747)` |

`kHanyuPinlu` 特別有價值：它給的是**每個讀音的使用頻次**，
這正是破音字排序需要的東西——「一」讀 `yī` 三萬多次，讀其他音少得多，
不需要另外找語料就能排出優先序。

**注音從哪裡來？** Unihan 沒有直接的注音符號欄位，但拼音 → 注音是
**確定性對應**（不是創作，是事實），一張幾百行的轉寫表就能完成
（RIME 的 `zhuyin.yaml` 做的正是這件事）。所以：

```
Unihan kMandarin (44,355 字)
      + 拼音→注音轉寫表（自建，數百行，確定性對應）
      + kHanyuPinlu（破音字頻次）
      = 完整的注音讀音表
```

**這條路完全不需要 McBopomofo 或 libchewing。**

## 三、詞庫與詞頻表：從語料自己算

這是三張表裡唯一需要**語料**的，但語料來源很多，而且統計方法本身是公開的。

### 3.1 詞頻公式（McBopomofo 的公開做法）

```
freq(k) = log10( 2.7^(len(k)-1) × occ(k) / norm )
```

- `2.7^(len(k)-1)`：**長度補償**。沒有它，長詞的出現次數永遠低於短詞，
  分詞器會系統性偏好逐字解
- `occ(k)`：詞 k 在語料中的出現次數
- `norm`：正規化常數

**這條公式不需要授權**——它是數學。本專案的 `data/bopomofo-lm.tsv` 取用的是
採用這條公式的管線輸出，所以分數裡已經含了補償（見 [06](06-engine-design.md)）。

### 3.2 一個必須處理的陷阱：子字串虛假計數

「台灣」出現 1,000 次，其中 800 次其實是「台灣大學」的一部分。
若不扣除，單獨的「台灣」會被高估。

McBopomofo 的 `exclusion.txt` 就是為此存在：把「被包含在更長詞中」的計數扣掉。
自建管線時這一步不能省，否則短詞會氾濫。

### 3.3 斷詞庫：無監督新詞發現

沒有現成詞庫時，可以從語料自己長出來：

```
候選 n-gram（n = 2..6）
   ├─ 互信息 MI(x,y) = log [ P(xy) / (P(x)·P(y)) ]     ← 內部結合緊密度
   └─ 左右鄰接熵  H_left, H_right                        ← 邊界自由度
   篩選：MI > 閾值 且 鄰接熵 > 閾值
   ▼
候選新詞 → 人工複核 → 詞庫
```

這是中文資訊處理的標準做法（「新詞發現」），工具鏈在 jieba、HanLP 等專案裡
都有可參考的實作。**它輸出的是統計量，不是別人的詞表。**

### 3.4 語料來源（全部開放）

| 來源 | 授權 | 備註 |
|---|---|---|
| 維基百科／維基詞典 dump | CC BY-SA | 量大、涵蓋現代用語，需注意 SA 的傳染性 |
| 政府開放資料（立法院公報、政府出版品） | OGDL-1.0 | 台灣用語、公文語體 |
| 教育部語料庫 | 需個別確認 | 華語教學語體 |
| 開放街圖、開放原始碼註解 | ODbL／各專案 | 專有名詞 |

> ⚠️ **法律要點（非法律意見）**：詞頻統計的**輸出**（「某詞出現 N 次」）
> 通常被視為事實性資料，而事實不受著作權保護。但「以受著作權保護的語料
> 產出統計量」是否構成衍生作品，各司法管轄區見解不一。
> **採用受 CC BY-SA 之類傳染性授權的語料時，必須先確認這條界線。**
> 若要有完全乾淨的來源，應以政府開放資料（OGDL）與自有語料為主。

## 四、這對專案意味著什麼

### 對授權分析（[04](04-data-and-licensing.md)）的修正

04 的文件讀起來像是「我們在別人的授權縫隙裡求生」。正確的理解是：

| 情境 | 對策 | 成本 |
|---|---|---|
| 上游都健在（現在） | 直接用 McBopomofo（MIT） | 0 |
| McBopomofo 改變授權／消失 | 換 libchewing-data（CC BY 4.0） | 低（格式轉換） |
| 兩個都不可用 | **從 Unihan + 自建語料重建** | 中（數週） |

**第三條路的存在，讓前兩條路的談判地位完全不同。** 我們接受 MIT 是因為它方便，
不是因為沒有它就做不下去。

### 對「護城河」的修正

自然輸入法的護城河**不是資料**。它的詞庫可以從語料重建，
它的引擎（v10–v13）甚至建在開源的 OpenVanilla 與菸草注音引擎上（見 [01](01-competitive-analysis.md) §5.1）。

它真正的護城河是 **35 年的脈絡會意法調校**、**桌面整合的細節打磨**、
**司法院體系的實務地位**、以及**使用者 30 年累積的個人詞庫與肌肉記憶**。
這些都不是抓資料能複製的——這也正是 [05 路線圖](05-roadmap.md) 把
「個人化學習」排在很前面的原因。

### 具體行動

| 項目 | 何時做 |
|---|---|
| 把 Unihan 讀音表接入，作為讀音的第二來源（交叉驗證 + 補罕用字） | M2 之後 |
| 用 `kHanyuPinlu` 建立破音字優先序 | M2 之後（可取代教育部《一字多音審訂表》，授權更乾淨） |
| 自建簡繁表作為 OpenCC 的交叉驗證 | M8 |
| 自建語料管線（MI + 鄰接熵新詞發現） | 當需要台灣本地新詞時（M8+） |

**現在都不做。** 目前的資料（169,604 詞條）已經足夠跑出 100% 讀音準確率
（見 [06](06-engine-design.md)），自建資料層是**保險**與**未來的擴充路徑**，不是當務之急。

> 這一節的價值在於：當有人問「你們的詞庫是跟人家拿的，那授權怎麼辦」時，
> 答案是「**我們可以自己做，而且已經知道怎麼做、用什麼來源、公式是什麼**」。
