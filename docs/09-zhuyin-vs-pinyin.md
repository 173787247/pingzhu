# 注音与拼音的效率比较（量化）

> 一句话结论：**注音在同等条件下少约 6% 的按键，而差距的来源不是「打字比较快」，
> 是「比较不需要选字」。**

这份文件回答一个具体问题：既然拼音的使用者多那么多，为什么还要做注音输入法？
答案是量出来的，不是感觉出来的。

```bash
node tools/zhuyin-vs-pinyin.mjs          # 重現全部數字
node tools/zhuyin-vs-pinyin.mjs --json   # 機器可讀
```

---

## 1. 方法

### 资料

`data/bopomofo-lm.tsv`——169,604 条词，每条都带注音读音与词频分数。这是引擎实际使用的
语言模型，不是另外找的语料。

**同一批词、同一组词频，只是换一种编码。** 这是最关键的一点：两边的「目标词」完全一样，
所以量到的是编码本身的差异，不是语料差异。

### 拼音读音怎么来

由注音系统性推导（[`engine/src/pinyin.ts`](../engine/src/pinyin.ts)），不是查表：

```
ㄓㄨㄥ  -> zhong      ㄐㄩㄣ  -> jun      （j q x 之後 ü 寫成 u）
ㄒㄩㄥ  -> xiong      ㄌㄧㄡˊ -> liu      （韻母縮寫）
ㄋㄩˇ   -> nv         ㄕ    -> shi      （空韻寫成 i）
```

169,604 条中，注音无法解析 **0 条**，拼音对应缺漏 **17 条**（0.01%，罕见音节）。

**声调一律不计。** 这是对拼音公平的作法——实际上没有人在拼音里打声调。
而注音**必须**打（一声除外），这正是差异的来源之一，不是我们额外加的惩罚。

### 五个指标

| 指标 | 定义 |
|---|---|
| 组字按键／字 | 拼出这个词要按几键。注音在大千键盘上一键一个元件；拼音是字母数 |
| **有效按键／字** | 组字键 **加上选字键**。这才是实际打字速度 |
| 首选正确率 | 该词是不是它那个按键序列中词频最高的（是的话不必选字） |
| 前十个内找得到 | 该词在候选第一页里的比例 |
| 平均同码候选数 | 一个按键序列平均对应几个不同的词——**模糊度** |

选字成本模型：名次 1 不必选字；名次 r ≤ 10 按一个数字键；名次更后面要先翻页。
模型写在程式码里，可以直接改成你认为合理的值。

**全部 169,587 条都计分，没有抽样**，所以这些是精确值而不是估计值。

## 2. 结果

### 范围一：全部词条（含单字）

单字是同音最严重的部分——`ㄕˋ` 底下有几十个字。

| | 注音 | 拼音 |
|---|---|---|
| 组字按键／字 | 2.99 | 3.10 |
| **有效按键／字** | **3.17** | **3.58** |
| 首选正确率 | **77.26%** | 60.64% |
| 前十个内找得到 | 90.67% | 86.49% |
| 目标词平均名次 | **4.12** | 10.26 |
| 平均同码候选数 | **7.25** | **19.52** |
| 相异按键序列数 | 131,031 | 102,835 |

**有效按键比 1.129 —— 注音少 11.4%。**

### 范围二：2–4 音节、一字一音

与 `bench.mjs` 相同的范围，方便对照既有的实测数字。

| | 注音 | 拼音 |
|---|---|---|
| 组字按键／字 | 2.98 | 3.10 |
| **有效按键／字** | **3.01** | **3.20** |
| 首选正确率 | **90.67%** | 71.25% |
| 前十个内找得到 | 100.00% | 99.54% |
| 目标词平均名次 | **1.12** | 1.64 |
| 平均同码候选数 | **1.23** | **2.28** |

**有效按键比 1.063 —— 注音少 6.0%。**

### 方法自我验证

范围二的注音首选正确率是 **90.67%**。`bench.mjs` 用**完全不同的路径**——实际跑 Viterbi
解码器、抽样 5,000 个读音——量到的是 **90.38%**。

两条独立路径相差 0.29 个百分点。这说明「按同一读音内的词频名次」这个便宜的代理指标，
确实抓住了真实解码器的行为。

## 3. 差距从哪里来

**不是组字速度。** 2.99 对 3.10——注音只少 3.7% 的按键，因为两件事互相抵消：

- 注音**必须打声调**（一声除外），拼音不用
- 但注音把 `zh ch sh ang eng ong` 各压成**一键**，拼音要 2–5 个字母

```
你好    注音 6 鍵  /  拼音 5 字母     拼音少 1
中文    注音 6 鍵  /  拼音 8 字母     注音少 2
萬丹    注音 5 鍵  /  拼音 6 字母     注音少 1
```

**差距来自模糊度。** 平均同码候选数：注音 **7.25**，拼音 **19.52**——**2.7 倍**。

拼音丢掉声调之后，`shi` 要同时代表 是、时、事、市、世、式、视、示、士、势⋯⋯
注音的 `ㄕˋ` 只代表其中一部分，`ㄕˊ`、`ㄕˇ`、`ㄕ` 各自分开。

而且拼音还会**跨音节边界**碰撞：`xian` 同时是「先」和「西+安」。这种碰撞注音不存在，
因为音节之间有声调与结构把它们分开。

结果就是首选正确率差 **19.4 个百分点**（范围二），而每一分的落差都要用选字按键补回来。

## 4. 这份测量没有证明什么

严谨起见，把限制讲清楚：

**一、量的是编码，不是完整的拼音输入法。**
真实的拼音输入法（搜狗、微软拼音）有更大的模型与上下文，可以从语境恢复一部分模糊。
但**编码本身的碰撞是消不掉的**，只能在碰撞发生后猜得更准。所以这个差距是下界，不是等值。

**二、没有计入简拼。**
拼音使用者常打缩写（`nihao` → `nh`），这会降低拼音的按键数。注音也有类似的省略写法，
但这份测量两边都没算。要纳入需要另一组实验，因为简拼会**大幅提高**模糊度——那是另一个
取舍，不是免费的。

**三、语料是繁体。**
语言模型从繁体语料建立，所以反映的是那套词汇。比较本身是内部一致的（同一批词、
同一组词频、两种编码），但**不能推论到简体语料**上。

**四、选字成本是模型，不是实测。**
「名次 r 要花几个键」用了一个简单模型。模型在程式码里，可以改。不过差距的方向很稳健：
即使把选字成本设为 0（完全不必选字），组字按键仍然是 2.98 对 3.10——注音还是少。

## 5. 为什么这仍然值得做

市场小是事实。但「小」不等于「没有价值」，而且这里有一个常被忽略的结构性理由：

**注音的模糊度低，是因为它把声调写出来。** 声调是中文的资讯，不是冗余。
丢掉它，就要用更大的模型、更多的上下文、更多的选字去补回来——那些成本是**使用者每次
打字都在付**的，不只是开发者付一次。

所以对**已经会注音的人**（台湾、以及像本专案维护者这样长期在外的使用者），注音不只是
习惯，是在同等条件下更省力的编码。

这个专案要做的，是把那个省力保留下来，同时接到现代的输入法框架上——
而不是要求使用者改用拼音。
