# 输入法 × Agent：能做什么，不做什么

这份文档回答一个问题：**联想词能不能接上 AI agent**。

写它是因为 2026-11-18 那天实测得到了一次完整的联想词输入（见第五节），随后讨论
自然延伸到了「agent 能不能帮我预判下一句」「AI 眼镜能不能一起用」。这份文档把结论
定下来，免得每次从头聊一遍。

同样是结论与理由，不是路线图。里面列的东西，做了的写明做了，不做的写明为什么不做。

---

## 一、现在有的东西

联想词已经能用，靠的是一张**统计接续表**（`data/bigram.tsv`，8850 行）：

```
词 <TAB> 接续词 <TAB> 频次
```

由 `tools/build-bigram.mjs` 从 12 篇国务院公文（87,525 字）统计出来。送出词之后，
从已送出文本的尾部由长到短试，命中表里的第一条就是。

**它有三个性质，决定了很多事**：

| 性质 | 意味着什么 |
|---|---|
| **离线** | 不需要网络，断网也能用 |
| **即时** | 微秒级，不进入打字的延迟路径 |
| **只读** | 不写盘、不上传、不联网 |

**三个平台在用**：web 试打版、HarmonyOS 真机、Windows TSF 真机。

### 它的天花板也是这三条

**它只知道「前一个词」**。不知道你在写什么文档、不知道上文三句话讲了什么、不知道
你昨天写过类似的段落。**所以「发展」后面永远接「提升」（14 次），不管你在写什么。**

---

## 二、接 agent 能补上什么

| 现在 | 接 agent 之后 |
|---|---|
| 只看前一个词 | 看整段、整篇、甚至历史 |
| 频次最高的接续 | **按当前上下文给**建议 |
| 单字或词 | **整句补全** |
| 固定不变 | 会随你写的东西变化 |

**这正是自然輸入法 V13 卖的「長句聯想」**（`docs/11-m8-requirements.md` 记着它
1995–2023 的功能表与定价）。不是什么新想法。

---

## 三、两层结构 —— 这是核心结论

**不能把模型放在打字的路径上。**

输入法对延迟的要求是「按下去就出字」。统计表是这个速度，网络模型不是。**一旦让
模型参与出字，输入法就变成「打字要等一下」** —— 那不可用。

所以分两层：

```
第一层：统计接续表        ← 即时、离线、隐私安全，永远在
第二层：模型补全（异步）   ← 停顿之后才跑，结果作为「建议」呈现
```

**第二层的触发条件是「停顿」，不是「按键」**：

- 用户停手 1.5–2 秒
- 且当前段落有足够上下文（比如超过 10 个字）
- 才发一次请求

**回来的东西不插进文档** —— 它显示在联想窗里，**用户按数字键才接受**。这一点和现在的
联想词完全一样，只是候选来源多了一个。

**延迟被藏起来了**：用户在打字时，第二层在后台跑；用户停下来看的时候，结果已经到了。

## 四、四条硬约束

这四条不是建议，是**做这个功能的前提**。任何一条不满足，这个功能不该上。

### 1. 默认关

**装完不采集、不联网**。用户明确打开才算同意。

**理由**：输入法在系统层收每一个键 —— 它跟键盘记录器的机制**完全一样**（这不是比喻，
是它的工作方式）。给一个本来就能看全的东西装上理解能力，起点必须是「用户主动要求」。

### 2. 看得见

**状态栏要有明确指示**（比如托盘图标变色），**能一键关**。

**理由**：一个你看不见的采集中间态，和没有开关是一样的。

### 3. 本地优先

**模型优先跑本地**（Ollama / llama.cpp 那一套）。走云端时必须：
- 在设置里写明「会发送到 X」
- 发送前让用户看过一次
- 能按应用排除（比如密码框、银行网站永不发送）

### 4. 不打断打字

**见第三节**。第二层的任何结果都不能进入按键路径。

## 五、实测记录（2026-11-18）

真机验到的完整链路：

```
打 ㄏㄠˇ → 空白送出「好」
  → 联想窗出现「接下：本 发展 房 生态 生活」
  → 按 2 → 「发展」插入到「好」后面
  → 联想窗换成「发展」的接续「提升 改革 第十 道 型」
  → 继续按数字键…
```

连点八次得到：

```
好发展改革创新的知识产权保护规则和政策措施
```

光标始终在末尾，联想跟着每次追加走。

**这串话本身就说明了统计表的局限**：它能拼出通顺的公文句子，因为语料就是公文。
换成写情书、写代码注释，它就不行了 —— **它只学会了那 12 篇公文**。

## 六、为什么不碰 AI 眼镜

**技术上做得出来，做出来也不好用，而且不该由这个项目做。**

### 技术上的四个死结

1. **电池** —— 摄像头 + 麦克风 + 定位全开，撑不过几小时。这是物理限制。
2. **端侧算不动** —— 多模态模型跑在眼镜上，现在的芯片功耗、散热、内存全不够。
3. **上云有延迟** —— 语音助手对延迟的要求是「像人一样接话」，几百毫秒到几秒不行。
4. **多模态融合没有成熟开源方案** —— 语音、视觉、位置三路合成一个「你在干什么」的
   理解，各家都在摸索。

### 一个不是技术的问题（但必须写下来）

**输入法只在你打字时看 —— 你有意识地在输入。眼镜是一直戴着、一直看、一直听，
还知道你在哪 —— 没有「不打字的时候」。**

**而且它躲不掉**：输入法可以「不装」；眼镜戴上之后，**被拍的人不知道**。

这两件事性质不同：前者是「你自己选择输入的东西」，后者是「你被动录下的一切」。
输入法那个功能还能用第四节那四条约束控制住，眼镜那个控制不住。

**所以这个项目不碰眼镜。** 不是因为难，是因为它把这个项目的性质变了。
