上游来源：**McBopomofo（MIT）**，即 `research/04` 记的 `BPMFMappings.txt` /

### 1.2 ★ 本轮的新发现：资料层有一道上限，它打在【硬需求】上

`data/build.mjs` 第 104 行：

```js
const MAX_PER_READING = Number(process.env.PINGZHU_MAX_CANDIDATES ?? 100);
```

**每个读音只留分数最高的 100 个词，其余全丢。**

对多音节读音，这是纯粹的排序决定；**对单音节读音，这是一次删除** ——
被删的字**不在引擎读的任何档案里**，按几次键都到不了。

> **★ 本节写于实测之前，措辞已被 §2.1 修正两处（保留原文以便回溯）**
>
> ```
> 推测（上一会话的脚本注释）   ㄩˋ 有「几千个」同音字，上限丢弃大部分
> 实测（§2.1，真跑）           全网最深读音 236 条；超过 100 的只有 15 个读音；
>                              上限实际只删 595 条，且全部并列在底线分 -7.904
> 推测                          stats.json 的 699 混在一起，看起来人畜无害
> 实测                          699 里 595 是上限删的、104 是分数过滤的；
>                              两类都确实存在，但量级都比预期小两个数量级
> ```

而 `stats.json` 记的是 `dropped_low_probability: 699` —— 只数「被丢掉的行数」，
**不区分「多音节排到 100 名之外」与「单音节根本没有第 101 个候选可显示」**。

### 1.3 ★ 与验收标准的关系（这条决定了它算不算「活」）

`START-HERE.md` §验收标准 把判据分成两半：

```
使用者要的字符 → 必须能用按键打到（候选表里有）   ← 硬需求，破了就是缺陷
不用管它排第几 → 排第一省一个键，排第十多按一个键 ← 软成本，可以权衡
```

**上限 100 破的是硬需求那一半**（候选表里没有 → 打不到）。
这也正好绕开了「别用首选正确率当验收标准」那条禁令 ——
**它完全不涉及排名，只涉及存在与否。**

### 1.4 ★ 其实是三道闸，不是两道（本轮实测补上第三道）

| 位置 | 值 | 含义 | 现在是否起作用 |
|---|---|---|---|
| `data/build.mjs` `MAX_PER_READING` | **100** | 建资料时每读音留几个词 | ★ **是**（实际天花板） |
| `engine/src/dictionary.ts` `maxCandidatesPerReading` | **128** | 载入时每读音最多收几条 | 否（被 100 挡住） |
| `core-rs/src/dictionary.rs` `max_candidates_per_reading` | **128** | 同上（Rust 侧） | 否（被 100 挡住） |
| `engine/src/engine.ts` `CANDIDATE_CAP` | **200** | 引擎一次能取出几个候选 | 否（被 100 挡住） |
| `core-rs/src/engine.rs` `CANDIDATE_CAP` | **200** | 同上（Rust 侧） | 否（被 100 挡住） |

**★ 第三道闸（128）现在看不见，但它是一颗定时炸弹**：
因为数据被压到 100 行，没有任何读音越过 128，所以这一行永远不触发。
**可是一旦把数据上限抬到 128 以上，128 就立刻变成新的天花板** ——
而它在 `dictionary.ts` / `dictionary.rs` 里是个没有理由说明的常数，
引擎自己的 `CANDIDATE_CAP` 却是 200。

```
实测（真档案 + 真引擎）：
  数据 cap=200 的档案，载入器 128 → ㄧˋ 只能看到 100 个候选
  数据 cap=200 的档案，载入器 200 → ㄧˋ 能看到 136 个候选
```

**⇒ 两级上限必须一起动，否则抬了数据层却只换来 128。**

## 二、★ 本轮实测结果（2026-10-08，全部是真跑出来的数字）

### 2.1 上限 100 到底删了什么 —— 比想象中小得多，但确实破了一半硬需求

`research/tools/cap-scope.mjs`（本轮新写，只输出统计，不打印语料）：

```
上限之下被删的条目          595   （原始 170,181 → 保留 170,163 的差额）
  · 单音节                  595   ← 全部
  · 多音节                    0   ← 一条都没删
涉及读音                     15 个（全部是单音节）
删除条目的平均名次           132.8
```

**为什么删得这么少**：`WebData` 里 **90.43% 的读音只有 1 个条目**，
只有 15 个读音超过 100。`stats.json` 那个 `dropped_low_probability: 699`
看起来吓人，其实只数「被丢掉的行数」，不区分单音节与多音节。

**★ 而 595 条全部并列在同一个分数上**：

```
15 个超限读音，每一个的 第100名 与 第101名 分数完全相同（都是 -7.904）
并列分数的条目数 = 包括第 100 名在内的整个尾部
```

`-7.904` 是这份资料的**底线分**：它在整份 `WebData` 里出现 18,413 次，
是出现次数最多的分数（第二名 `-6.61` 是 15,054 次）
—— 也就是上游对「没有频率信息」的字统一给的值。
所以第 100 与第 101 之间**没有任何排序信息**，档案保留哪 100 个是任意切。
**不是「模型认为前 100 个更常用」，是「排序到那里就打平了」。**

**★ 决定性的一个数字**：只看 BMP（普通中日韩汉字，U+4E00–U+9FFF），
最深的读音是 **96** 个字 —— **100 这条线正好切在普通字结束、
CJK 扩展 A/B 异体字开始的地方。**

**可达性分两级**（`cap-scope.mjs`）：

```
被删的 595 个字中，换个读音仍然打得到的        110
在任何读音下都打不到的                        485
```

**★ 但这 485 个不是「很常用的字被误删」**：它们的 chars.tsv 名次
（另一份独立的频序表）分布是 —— 1–10 名 4 个、11–30 名 16 个、
31–60 名 21 个、61–100 名 159 个、101–200 名 355 个、201+ 名 32 个。
**而且它们同时是：上游分数 = 底线、名次 ≥101、多数落在 CJK 扩展 A/B。**
两份独立的排序都说它们罕见，只有「底线并列」让它们看起来挤在第 100 名附近。

### 2.2 ★ 抬上限的代价与收益（`research/tools/cap-raise-trial.mjs`，本轮新写）

试算方式：从同一份 vendor 源重建，**写到内存比较，不碰发行档**。
两个轴一起量 —— 数据上限（build）与载入上限（dictionary）。

```
data cap  loader   行数        字节    相对发行档  新可打字数
100          128  169,604   6,433,982       +0          0   ← 现状
100          200  169,604   6,433,982       +0          0   ← 只抬载入器没用
128          128  169,946   6,440,413   +6,431        251
128          200  169,946   6,440,413   +6,431        251   ← 数据先撞上 128
150          200  170,077   6,442,815   +8,833        335
200          128  170,163   6,444,359  +10,377        332   ← 抬了数据却被载入器吃掉 60 个
200          200  170,163   6,444,359  +10,377        392   ★ 两级对齐
1000         200  170,303   6,446,751  +12,769        430
1000        1000  170,303   6,446,751  +12,769        ~430   （上限实质消失）
```

**★ 三个结论：**

```
① 载入器的 128 是【独立的第二个瓶颈】：数据 cap=200 时，
      载入器 128 → 332 个；载入器 200 → 392 个   ← 它自己吃掉 60 个
   （真档案 + 真引擎复核：数据 cap=200 时 ㄧˋ 的候选数，载入器 128 → 100、200 → 136）

② 代价侧的原本理由（档案大小）实测不成立：全量解禁只 +12,769 字节 = +0.20%；
   载入时间 164–250 ms 全在噪声内（跑一次的量测，不构成趋势）

③ 该停的地方是 200：无论载入器开多大，数据 cap 从 200 抬到 1000
   只再多 38 个字（392 → 430），而 200 正好等于引擎自己的 CANDIDATE_CAP
```

**★ 收益侧是 392 个**此前**任何读音都打不到的**字（两级都对齐到 200）。

### 2.3 ★ 一个重要的性质：这个改动不会让任何现有候选变差

上限只**追加**条目，不做替换 ⇒ 前 100 名逐字节不变 ⇒
**所有现有候选的排名与出字完全不变**。所以「换字频只值 0.4%」那条实测
（讲的是排名）与它不冲突 —— **这条讲的是「有没有」，那条讲的是「第几名」。**

### 2.7 第三轴：候选字表里有、字词表里没有的字（551 / 482 两个口径）

上一会话留下的 `reach-audit.mjs` 跑通后给出第三条轴：
`bopomofo-chars.tsv`（**频率序**候选字表）里有 551 个字，在 `bopomofo-lm.tsv`
（**分数序**字词表）里完全找不到。

**★ 两条轴的差（551 vs 482）是口径，不是矛盾**：`reach-audit.mjs` 数的是
「条目」（同字可重复计），本节数的是「不同的字」。两个数都留着。

**★ 关键判定 —— 这 482 个字的出处（本轮实测）**：

```
chars.tsv 里、LM 里没有的字            482
  · 在 vendor 源里有                  482   （不是继承缺口）
  · 其中在某个读音排在前 100 名内        2   ← 不是上限造成的，见下
  · 只在 100 名之外出现                480   ★ 上限正是原因
  · vendor 源里也没有                    0
```

**⇒ 这 480 个字抬上限就能救回来**（它们与 §2.1 那 485 个高度重叠，
是同一批字在两条不同的量法下面的呈现）。剩下那 **2 个**见下。

**★ 那 2 个异常查清了 —— 是「上限按行算、不按字算」的直接后果**：

```
vendor 源里排在第 99 与第 100 名、却不在发行档里：
    ㄧˋ  㑊  rank 99
    ㄧˋ  㔴  rank 100
（两个都不在任何其他读音下出现 ⇒ 发行档里彻底没有它们）

原因：`data/build.mjs` 是对【原始行】排序后取前 100 行，
      而 ㄧˋ 的前 100 行里有 15 条是同字重复（100 行只对应 85 个不同的字）。
      ⇒ 15 个名额被重复行占掉，把 㑊 / 㔴 挤了出去。
```

**⇒ 修法很便宜**：`build.mjs` 在排序前先去重（同一个 `reading` 里同样的
`word` 只留一条），上限就变成「100 个**不同的**字」。这样连那 2 个也回来，
而且上限的语义变得可解释（现在这条 100 的语义是「100 行，可能是 85 个字」）。
